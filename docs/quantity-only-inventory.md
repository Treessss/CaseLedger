# 公共数量库存（2026-10-14）

本规则替代此前按订单优先级预分配、保护售后占用和开始打包锁定库存的方案。

## 数量与需求

- 在库：合格采购入库 + 手动调整 - 实际出库；历史已出库数据保持原有扣减口径。
- 原单、售后单都只记录需求；采购清单的订单关联仅用于追溯采购来源，不赋予库存所有权。
- 需求：有效、未实际出库的原单及售后商品数量；退款、取消、删除等按既有业务规则排除。
- 采购中：已确认采购但尚未合格入库的数量；草稿、货损不算在途合格货。
- 待补：汇总需求扣掉在库与采购中，17/18 Pro、17/18 Pro Max 在相同商品与颜色/配置内按通用数量抵扣。
- 在途采购抵扣先覆盖所有同型号的剩余需求（含售后），再把余量用于通用型号；例如盘点减少17 Pro Max，而18 Pro Max另有同型号需求时，不能先借走18的在途货把缺口显示在18。此规则不限制扫码使用通用实物库存。
- 查看需求可跳转对应订单/CF 单；不再展示占用、打包锁定、空闲分配。
- 原有库存绑定接口停用；历史关联保留供追溯，不删除旧数据，也不限制出库。

## 出库与撤回

- 原单、售后都按实物数量校验，谁先实际扫码谁取得最后一件；数据库店铺锁保证串行扣减。
- 订单优先级只影响补货需求参考顺序，不限制实际出库。
- 读取列表和开始装箱核对都不占库存。装箱记录是核对任务，不是库存预留。
- 一个订单能出库，不代表其他共享同一库存的订单也能随后出库；每次扫描重新核实数量。
- 批量面单只导出公共数量能覆盖的建议批次，避免一件货打印给多个订单；建议不预占库存，不限制其他单直接扫码。
- 通用型号直接扣减实际来源型号，不生成虚假的型号转换入库或订单间库存转让。
- 多包裹必须先整单货齐；第一包扫码记整单数量扣减，后续包裹只完成扫描状态，避免重复扣减。
- 撤回原单按不可变出库流水返还；撤回售后按扫码时保存的实际来源型号快照返还。
- 核对后订单变体/数量改变时必须重新核对；不能把旧装箱内容直接当作新商品发走。
- 历史部分扫码但无实物扣减流水的记录不能捐出货，先撤回/盘点核实后再操作。

## 联动与验证

- 原单采购状态、售后详情/列表、发货中心、面单下载及装箱核对统一使用实物可行性。
- 采购生成仍基于全店净需求一次抵扣库存和在途，避免多个订单重复使用一件货减少补货需求。
- 盘点可扣减到 0，不因核对任务而拒绝；库存变化后重新计算相关缺货需求。
- 无表结构变更，无需新增迁移；发布前备份主库，对比全部变体余额，不迁移/清零现有库存。
- 回归覆盖原单使用售后原先预留货、反向使用、相同最后一件竞争、跨店隔离、通用型号/腕链差异、重复扫码、多包裹扣减及撤回、分批采购入库与净补货。

## 扫码性能

- PostgreSQL 扫码只汇总本单相关变体的入库、调整和出库数量，不构造全店库存展示行。
- 数量不缓存：持有店铺锁后实时读取，与扣减流水处于同一事务，避免缓存过期导致超卖。
- 历史部分出库且无扣减流水的异常数据仍走原有完整核对路径，不以提速为由跳过安全校验。
