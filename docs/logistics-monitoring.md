# 物流轨迹核查

仓储作业 → 物流轨迹核查，沿用发货中心查看权限，强制补记另设 `tracking_force_outbound` 操作权限。管理员默认有权，子账号需单独授权。

## 三个标签

- 已出库、仅一条预报：严格只有一条 `Parcel information received`（或官方预报代码）；出库未满24小时显示观察中。出现真实运输事件后自动移出。
- 未出库、已有运输轨迹：按仓库状态，不按 Shopify 已发货状态。重复的预报事件不视为运输证据。
- 预报满15天、未送达：按首次可靠预报时间起算；不以最后轨迹时间起算。承运商历史截短时也保留已知最早预报日期。

数据分店铺保存。相同物流号若属于活跃 CF 售后单，归售后而非原单；物流号有多个活跃归属时拒绝补记。列表只读本地结果，不逐行请求承运商。失败保留上次可靠数据，页面显示失败数与核查时间。

三个标签页均在数据库分页前按原订单号的数字升序排序（不是按文字或预报时间），CF 售后包裹紧随同号原单；同号多包裹再按物流号及绑定ID稳定排序。兼容 `#`、前导零及超长数字，不依赖数值强制转换，旧非数字单号排在数字单号后。

## 15天异常处理标记

该页默认「未处理」，可切到「已处理」或「全部」，显示两类数量。员工在包裹行手动标记，记录UTC处理时间及操作人；误点可恢复未处理。状态保存在店铺下唯一物流记录上，针对同一运单，不跟随订单换号，不由轨迹刷新重置。

处理标记只表示客服/员工已经跟进，不代表已签收、已出库、已退款或已经补发。仍按既有间隔自动查轨迹；实际签收后从该异常分类退出。修改接口 `PATCH /api/logistics/{binding_id}/handling` 需要发货中心权限及本店铺访问权，严格校验布尔值，不能把非15天异常包裹标为已处理，不调用外部服务或改变库存。

迁移 `b6267c280e14`（前置 `212549c7f517`）新增 `tracking_records.handled_at/handled_by`，旧记录两字段默认NULL即未处理。操作人被删除时仅将引用置空，保留已处理时间。升级前备份，运行 `flask db upgrade`；已在空PostgreSQL库验证全迁移、结构一致及并发安全。

签收同时识别普通签收 `FPX_S_OK`、取件/授权放置签收 `FPX_S_OKCC`，以及未知末端代码中明确的已送达/已取得签名文本。待取件、派送中、派送失败、销毁、退回寄件人（包括写着 Delivered 的退件）不算客户签收。签收证据可来自任意一条历史事件，不只看最后一条。规则升级时可分批重判已有官方轨迹缓存，不重查全量订单，不伪造刷新时间，不改库存或出库状态。

一次性缓存修复：先备份，再运行 `PYTHONPATH=. venv/bin/python scripts/repair_tracking_deliveries.py --shop-id 1` 预览；核对后加 `--apply`。按主键分页、每批200条，只写该店铺物流记录，重复执行不会重复产生业务操作。此工具不属于定时任务。

## 后台更新

采用「事务变更队列 + 运单到期时钟 + 一次历史初始化」，不再每天全量发现，也不在每次刷新时读全店订单。订单物流、包裹、售后改号、出库/撤回/删除等相关 ORM 变更在同一数据库事务内写入 `tracking_changes`，同一订单合并为一条；事务回滚同步回滚，无 HTTP 或队列依赖。每分钟处理最多200条变更，只读取涉及的订单及同号关联订单。仅备注/价格修改不触发。

`tracking_discovery_states` 持久保存一次性历史发现游标，每次最多200个本地订单；完成后永不重新扫描。新增订单走变更队列，不重置历史游标。

每个运单保存 `next_check_at`，调度每分钟只从到期索引取数，实际查询频率如下：

- 新增/改号：新运单进入增量队列首次查询。
- 未出库且尚无运输轨迹：每小时。
- 刚出库、仅有预报：等出库满24小时再查询，之后每2小时。
- 已有实际运输轨迹（含15天未送达及未补记出库）：每6小时。
- 已送达：停止自动查询；更改仓库状态不会重新启动查询。
- 查询失败：30、60、120、240、360分钟退避，保留上次可靠结果。

正常增量任务每个最多40个号码，独立 `tracking` 队列；历史首次补查每个最多100个，只取尚未尝试的号码，独立 `tracking_history` 队列与 `tracking-history-worker`。历史失败重试由到期队列接管，不再从头补查。每个网络批次20个，最多3个并发，单次网络超时12秒。历史任务不阻塞正常任务。同一个运单跨标签共用记录，数据库运单租约防止两个任务同时重复查询；执行前再次检查是否到期/已结束/已失效，过时结果不会覆盖新变更或新查询。

「更新到期运单」只创建后台增量任务，即使旧客户端仍提交 `all` 也不能跳过缓存间隔。没有到期数据不发请求、不创建空任务。只有「强制刷新此单」允许指定一个绑定ID跳过时钟，包含已送达单；重复点击复用同号单条任务。数据库保存进度、错误、跳过数量和租约，5分钟恢复扫描防止工作进程中断导致永久卡住。关闭页面不终止后台工作。

## 批量补记（必须人工点击确认）

重新调用签名的4PX官方接口验证运输证据，每请求最多20个包裹。只扣实际可用库存，通用型号规则沿用现有系统；缺口进入 `tracking_outbound_audits.stock_result.shortages`，不创建虚假入库、不新增负库存。记录操作人、官方证据、实际扣减来源和缺口。

原订单通过不可变库存出库流水扣减，零库存也用零数量标记防止多包裹重复扣减；零标记不作为商品出入库流水展示。售后使用既有售后扣减流水与实扣快照；不修改原单、Shopify 或发送邮件。多包裹只补记选中的实际运输包裹，全部完成才整单已出库。重复操作幂等跳过。

撤回沿用扫码出库页，且仅归还实扣数量，不归还缺口。补记记录分页保留全历史，撤回后仍保存证据；可与原有出库/撤回流水对照。
