# 公共库存池、动态预分配与打包锁定

## 已确认的需求

- 库存以商品大类、颜色、型号为中心；采购关联订单用于追溯，不永久独占到货。
- 整单优先：人工加急优先，同级按创建时间；先分配可整单发出的订单，再预分配待凑单。
- A 等待 10 天、只缺一件而 B 未开始打包时，可优先补齐 A；B 已打包锁定或部分扫码时不得自动拆走。
- 只读查询不锁库存；开始打包才锁定整单。默认 30 分钟超时，取消可释放；部分扫码不自动过期。
- 出库需原子核验与扣减，历史出库记录不能被后续分配或盘点改写。
- 正常订单与 CF 售后单独立状态、明细、库存需求；商品/颜色/腕链配置不能错误合并。
- 同款同色同配置允许 iPhone 17 Pro ↔ 18 Pro、17 Pro Max ↔ 18 Pro Max；实际采用的库存变体要留痕。
- 看板：在库、采购中、需采购、可发货预分配、待凑单占用、打包锁定、空闲，支持大类/颜色汇总及明细。
- 在库 = 可发货预分配 + 待凑单占用 + 打包锁定 + 空闲；采购中/需采购不属于在库。
- 采购缺口按全店有效需求扣减公共库存和确认的在途采购；草稿不算在途，货损不算入库。
- 之前一次性移除的采购需求不能永久禁用；相关库存变化出现缺口时可重新进入采购。

## 实施与风险控制

1. 建立批量计算的规划器，区分历史物理账和软分配，输出数量及可追溯订单/采购明细。
2. 增加优先级、打包会话及出库库存明细，用正式 Alembic 迁移，空 PostgreSQL 库验证。
3. 库存看板接入规划器；采购候选、采购生成与确认使用同一需求口径。
4. 装箱核对新增开始/取消打包及优先级操作；扫码一次出库保持，扫码交易内重新验证。
5. 联动原单/CF、分批入库、兼容型号、多人并发、盘点、撤回出库、部分扫码保护。
6. 回归后才部署，不自动改写或重分配生产历史数据；旧流水保持可查。

## 必测案例

- A 旧单仅缺一件、B 新单齐货；A 优先整单备齐。
- A 即使拿 B 的货仍发不了；优先完成 B。
- B 已打包锁定/部分扫码，不允许抢走。
- 加急、锁定超时/取消、多员工争抢最后一件、重复扫码。
- 原单已出库但 CF 未出库，换品与漏发只扣售后实际商品。
- 17/18 通用与腕链/颜色不通用，实际库存身份保留。
- 确认采购在途、草稿、分批合格/货损/缺货、取消/退款与采购缺口。
- 盘点不释放已出库扣减；新出库不可变，撤回准确回补。
- 看板各层汇总、明细与平衡式，权限隔离、UTC/北京时区、iPad 13 交互和查询性能。

## 操作口径

- 「在库」是实物数量；「采购中」「需采购」不是现货，不能加到在库。
- 「可发货预分配」是能组成整单的现货建议，不代表已经绑定/已出库。
- 「待凑单」是暂用于缺其他商品的订单的现货建议，未打包可动态调配。
- 「空闲」是没有被上述需求预分配的现货；普通预分配是建议，不能理解为不可用实物。
- 查清单本身不锁货；「开始打包」锁住整单，其他员工不能重复领取。也可以不先领取，直接扫一枪，由出库交易自动验证并锁定后扣货。
- 原单的「优先发货」可将其提高到加急优先；同级按订单时间、ID 稳定排序。仍无法凑齐的旧单不拆散完整新单。
- 已备售后/部分扫码商品受保护。取消打包释放锁定但不扣货；部分扫码先整单撤回，不能自动超时释放。
- 用户要保留的旧采购单/关联订单继续用于追溯，不自动批量清理或替换历史账目。

## 部署注意

1. 服务器需先做私有数据库备份，部署新后端及前端，并执行同一 Alembic 迁移。
2. 不得覆盖服务器数据库为本地数据库；服务器是主环境，本次只需要代码和结构升级。
3. 新可发货队列会按公共库存重新计算，数量可能不同于旧永久绑定规则；这种变化不表示实物增加或历史订单被改写。
4. 测试脚本 `scripts/test_inventory_pool_postgres.py` 只创建带随机名称的本机测试库，不使用业务库；结束后清除该临时库。
