# 采购单与到货入库：现场操作复盘（2026-10-19）

## 方法

用管理员账号在生产环境只读走了一遍「采购管理 → 已生成清单 → 查看 / 清点到货 → 库存管理 → 手动入库」，并核对了 `purchase_lists`、`inventory_adjustments` 的真实数据。没有提交任何入库、调整或删除操作。

## 现状快照

- 35 张采购清单：已清点入库 20、待发起 8、已撤销 5、采购中 1、分批到货中 1；清单页只展示 30 张（撤销的不显示）。
- #45：244 笔订单、17 个商品大类、62 个颜色组、175 个变体、280 件，全部未清点。
- #44：193 个变体，合格 0 件、缺货 22 件，状态「分批到货中」，列表显示 `0 / 286`。
- #40：计划 203 件，合格 170 件、缺货 33 件，状态「已清点入库」，列表显示 `170 / 203`。
- 库存总览：需求 806、在库 206、采购中 544、需要采购 106。`806 − 206 − 544 = 56`，与 106 相差 50 件（不同型号之间不能互抵）。
- 手工入库记录：90 批「批量手动入库」共 142 件，另有 17 次「手动调整库存」正向增加 33 件。

## 核心问题

### 1. 三个入库入口，一本糊涂账（最严重）

现在增加库存有三条路，语义重叠、互不关联：

| 入口 | 位置 | 实际效果 |
|---|---|---|
| 采购清点入库 | 采购管理 → 清点到货 | 增加在库、关闭/推进采购清单、分配订单 |
| 批量手动入库 | 库存管理 → 手动入库 | 只写 `inventory_adjustments`，**完全不碰采购清单** |
| 调整（正数） | 库存管理 → 调整 | 同上，还能不带原因直接加库存 |

后果：采购到的货如果从「手动入库」进，库存加了，但采购单仍然是「采购中」，系统会同时把同一批货算进「在库」和「采购中」，导致「待补」偏小、订单被误判为已备齐，后续重复采购。生产上已经有 90 批走的是手动路径，这个风险不是假设。

### 2. 清单看不出「到没到、缺多少」

- #40 合格 170 / 计划 203，却被标成绿色的「已清点入库」。现场看到 84% 的进度条只会以为还有 33 件没到，实际是 33 件供应商缺货，已经结束到货。
- #44 有 22 件缺货，但列表显示 `0 / 286` + 「分批到货中」，看不出「0 合格、22 缺货、264 未到」。
- 列表只有「合格入库」一个数字，货损、缺货、未到全部不可见；`received` 状态既可能表示「全部到齐」，也可能表示「到齐一部分、其余缺货」，同名不同义。

### 3. 清点方式不适合现场

#45 要在一张弹窗里逐行处理 175 个变体，每个变体填 3 个数字（合格入库 / 货损 / 缺货补采），外加「到齐 / 剩余缺货 / 清空」三个按钮：

- 仓库实际只数「到了几件」，破损和少发是少数情况，却要求每一行都做三分法，认知负担高、极易串行填错。
- 没有扫码。商品有 SKU/条码，出库能扫，入库却只能靠产品 → 颜色 → 型号逐级展开、手点、手输。
- 关掉弹窗就丢失全部输入，175 行不可能一次数完；虽然支持分批保存，但没有「继续上次清点」的草稿。
- 顶部「全部到齐」会一次填满整张清单（有二次确认，但仍然是一键 280 件），松手就错。
- 底部「这是最后一批，剩余未清点按缺货处理」检查后，会把几百件一次性转成缺货并释放采购占用，只有一个勾选框兜底。

### 4. 缺货 / 货损没有下文

- 保存后缺货只是「回到待采购」这个大池子，没有「哪张单、哪个型号、还欠多少」的补采任务，过两天就找不到来源。
- 货损不区分「补采」还是「报损核销」，操作员不知道自己该做什么。
- 售后补发采购（CF 单）也混在同一池子里，来源只剩一个被截断的标签。

### 5. 库存四个数对不上，且没有解释

库存页每行是「需求 / 采购中 / 在库 / 待补」，但：

- 总览用「正在采购 / 需要采购 / 未出库需求」，行内用「采购中 / 待补」，同一概念两套词。
- 待补是按型号分别计算的，不能跨颜色/型号互抵，所以 `需求 − 在库 − 采购中 ≠ 待补`。总览差 50 件，磁吸指环 285−224−29=32 而待补是 40，现场只会认为系统算错了。
- 只有一段说明文字解释「不能跨型号互抵」，没有在数字旁标出「其中 50 件是型号结构错配」。

### 6. 历史脏数据没有出口

- #26 和 #27 的 `order_ids`、`items` 完全相同，是同一批 467 单 / 555 件的重复清单；#27 已入库 555 件，#26 显示已入库但实际 0 件。
- #25 已撤销，`order_ids/items` 都是空，却有 7 条清点记录、6 件合格入库。
- 8 张「待发起」草稿长期挂着，撤销清单默认不显示，既不能归档也不能合并。
- 这些数据会持续污染「已采购总览」「可发货」的判断，现场无法分辨哪张才是有效单。

## 目标操作流程（建议）

1. **建单**：一张清单 = 一次采购 = 一个供应商/一个包裹批次，带供应商、采购单号、预计到货、物流单号。
2. **到货**：仓库按包裹点「到货登记」，系统只显示这张单还没到的型号，按 SKU 排序，可扫码。
3. **清点**：每行只填「实到件数」，异常才展开填写「破损 / 少发」；支持暂存、继续清点、按颜色小计。
4. **结束**：明确显示「合格 X、破损 Y、少发 Z、未到 W」，未到按缺货处理前先给出汇总确认。
5. **补采**：缺货自动生成带来源的补采任务/补采清单；破损选择补采或报损。
6. **库存**：采购入库是唯一会推进采购单的入口；手动入库只用于盘盈/样品，必须选原因，并提示未关闭的采购单。

## 改造清单

| 优先级 | 改动 | 说明 | 风险 |
|---|---|---|---|
| P0 | 列表三段进度 | 合格 / 异常（破损+缺货）/ 未到，状态改为「待发起、采购中、到货中、已结束（有缺货 N）、已撤销」 | 低，前端+序列化字段 |
| P0 | 库存口径文案 | 「需求 / 已采购未到 / 在库 / 还差（按型号）」，公式 tooltip，结构错配提示 | 低 |
| P0 | 清点单数量 + 异常展开 | 默认只填实到数，破损/少发折叠；草稿自动保存；全部到齐需二次确认并显示件数 | 中，前端为主 |
| P0 | 手动入库加护栏 | 与未关闭采购单重叠时提示并引导到采购清点；调整正数需原因 | 中，前后端 |
| P1 | 清单元数据 | 供应商、采购单号、预计到货、物流单号/包裹数、备注；按状态/供应商/缺货筛选 | 中，需迁移 |
| P1 | 缺货补采闭环 | 按来源清单聚合缺货，一键生成补采单；补采入库自动核销 | 中高，后端 |
| P1 | 数据治理 | 重复清单检测、撤销单禁止再入库、草稿归档/合并、CF 标签独立列 | 中 |
| P2 | 扫码入库 / 包裹级到货 | SKU/条码扫描定位并累加；按包裹登记到货 | 高，需现场联调 |
| P2 | 库存缺口明细页 | 按变体列出需求、在库、采购中、还差、需求订单 | 低 |

## 建议的第一批（1–2 天，可先上线）

只动「看得懂、不会改错数」的部分：

1. 采购清单列表增加合格/货损/缺货/未到四列与三段进度条，修正状态标签（#40 显示「已结束 · 缺货 33」）。
2. 清点弹窗改为「实到数量」主输入 + 异常折叠，增加本地草稿与「继续上次清点」，全部到齐二次确认显示总件数。
3. 库存页四个指标改名并加公式提示，显示「其中 N 件为型号结构错配」。
4. 已撤销清单可筛选查看，重复清单/撤销单入库给出显式拦截提示。

第二批再做「入库入口收敛 + 缺货补采闭环」，第三批做供应商/包裹/扫码。这样现场先能对上账，再改流程。
